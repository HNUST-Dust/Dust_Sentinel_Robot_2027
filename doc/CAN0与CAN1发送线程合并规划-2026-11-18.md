# CAN0 与 CAN1 发送线程合并规划

日期：2026-11-18。

对象：当前下位机工程 `project/thread/can/trd_can_tx.cpp` 中的 CAN0、CAN1 两个发送线程。

本次只写规划，不修改代码、配置或其他文档，不构建、烧录、提交或推送；不修改上位机和公共子树。后续实施范围为该文件及本项目 Kconfig 中必要的 `select POLL`；实施仍需另行授权，不增加目录、模块或独立架构层。

## 1. 目标与保留边界

将两个发送线程合为一个线程，同时保留两条独立发送队列、两个 CAN 实例、原组帧格式和发送失败处理。

合并后的结构：

```text
user_can1_msgq ──┐                 ┌── user_can1.Send()
                ├── 一个 Task() ──┤
user_can0_msgq ──┘                 └── user_can0.Send()
```

需要保留的具体行为：

| 项目 | 当前行为 | 合并后的要求 |
| --- | --- | --- |
| 生产者接口 | 分别写入 `user_can0_msgq`、`user_can1_msgq` | 不改调用方，不合并队列 |
| 队列顺序 | 每路按 FIFO 取出 | 保持每路 FIFO，不根据 ID 重排 |
| 取消息 | `k_msgq_get(..., K_NO_WAIT)` | 保持非阻塞取消息 |
| 单拍处理 | 持续取消息，直到队列暂时为空 | 仅排空本次事件报告就绪的队列，然后重新等待 |
| 组帧 | `id = msg.tx_id`、`dlc = 8`、复制 `data[8]` | 保持相同字段和数据 |
| 发送参数 | `Send(&tx, K_MSEC(1))` | 保留原 timeout 参数 |
| 发送失败 | 打印对应总线与 CAN ID；不重新入队、不重试本帧 | 保持原处理，继续处理后续消息 |
| 成功含义 | `Send()` 返回的是提交结果 | 不改成“等待电机回复”或声称电机已经执行 |
| 线程配置 | 两个线程均为 `K_MSEC(1)`、`ThreadPrio::High` | 保留名称 `can` 和 High 优先级；框架周期改为 `K_NO_WAIT`，由 `k_poll()` 阻塞等消息 |
| 初始化 | CAN1 后 CAN0，检查设备、初始化、绑定各自 RX 回调 | 保持顺序、日志和失败返回路径 |
| 注册 | `can_init`、`can_start` | 保留阶段、级别、失败策略及名称 |

`topic::to_can_tx::Message::version` 目前没有参与组帧或发送判定。本次仍不为它增加过滤、去重或覆盖策略。

## 2. 当前源码依据

### 2.1 两个发送线程

文件：[trd_can_tx.cpp](../project/thread/can/trd_can_tx.cpp)。

- `thread_` 运行 `Task()`，处理 `user_can1_msgq`，使用 `user_can1`。
- `thread_can0_` 运行 `TaskCan0()`，处理 `user_can0_msgq`，使用 `user_can0`。
- 两个任务都是非阻塞取队列，逐帧组装并调用 `Send(..., K_MSEC(1))`。
- `thread_start()` 当前分别启动 `can`、`can0`。

### 2.2 外部接口，只读核对

- 公共 `framework/topic/to_can_tx`：两条队列各有 16 个消息槽位。队列属于独立存储，不能因为合并消费者就删掉其中一条。
- 公共 `Can::Send()`：调用 `can_send(..., tx_callback, this)`，返回调用是否成功；发送完成仍由底层回调处理。
- 公共 `Thread<>`：默认请求栈大小为 1024 B，实际对象还包含线程控制和统计等成员；当前周期等待是在任务返回后调用 `k_sleep(task_.period)`。
- 当前 HPM CAN 发送实现包含信号量和互斥锁等待，同一个 timeout 参数可能用于多个步骤。因此 `K_MSEC(1)` 不能直接解释成整个 `Send()` 绝对不超过 1 ms。

以上只是本规划的行为依据，不授权修改这些公共实现。

## 3. 推荐方案：根据就绪事件处理对应队列

一个线程通过 `k_poll()` 等待两条队列。事件类型为 `K_POLL_TYPE_MSGQ_DATA_AVAILABLE`，模式为 `K_POLL_MODE_NOTIFY_ONLY`。等待返回后必须检查每项事件的 `state`，只处理报告就绪的那条队列。

| 本次事件状态 | 本轮处理 |
| --- | --- |
| 只有 CAN0 就绪 | 只从 user_can0_msgq 取消息，只调用 user_can0.Send() |
| 只有 CAN1 就绪 | 只从 user_can1_msgq 取消息，只调用 user_can1.Send() |
| 两项均就绪 | 分别处理两个就绪队列；单线程顺序执行 |
| 两项均未就绪 | 继续阻塞等待，不调用任何发送函数 |

**不能在任一路唤醒后无条件调用两路发送函数，也不采用交替轮询两条队列的方案。** 未就绪的队列本轮不取、不发。

保留原有排空逻辑：对已就绪的队列持续执行 `k_msgq_get(..., K_NO_WAIT)`，每条消息按原格式发送，直到该队列暂时为空。`k_poll()` 只通知就绪，不替调用者取消息。

```text
复位两项事件状态
  ↓
k_poll(两个队列事件, K_FOREVER)
  ↓
检查 CAN1 事件：就绪才处理 CAN1 队列
检查 CAN0 事件：就绪才处理 CAN0 队列
  ↓
返回 Continue，下一拍重新等待
```

事件在原文件声明为 `static k_poll_event events_[2] {};`，在原初始化流程中分别绑定 CAN1、CAN0 队列，每次等待前将 state 复位为 `K_POLL_STATE_NOT_READY`。不创建新的层或中转队列。

### 3.1 对应队列的发送处理

以下为规划中的代码示意，保留原来的 while 取消息、8字节组帧、发送超时与失败处理：

```cpp
/**
 * @brief 处理已就绪队列中的待发送消息
 * @param can   对应 CAN 实例
 * @param msgq  对应发送队列
 * @param name  日志中的总线名称
 */
static void SendPending(Can& can, k_msgq* msgq, const char* name)
{
	topic::to_can_tx::Message msg{};

	while (k_msgq_get(msgq, &msg, K_NO_WAIT) == 0)
	{
		can_frame tx {
			.id = msg.tx_id,
			.dlc = 8,
		};

		std::memcpy(tx.data, msg.data, 8);

		if (!can.Send(&tx, K_MSEC(1))) {
			DUST_LOG_ERR("%s tx fail id=0x%x", name, static_cast<unsigned>(tx.id));
		}
	}
}
```

发送失败仍只记录原总线名称和CAN ID，不重新入队、不增加重试，继续处理该就绪队列中的后续消息。

### 3.2 事件初始化与任务

```cpp
k_poll_event_init(&events_[0], K_POLL_TYPE_MSGQ_DATA_AVAILABLE,
                 K_POLL_MODE_NOTIFY_ONLY, &user_can1_msgq);
k_poll_event_init(&events_[1], K_POLL_TYPE_MSGQ_DATA_AVAILABLE,
                 K_POLL_MODE_NOTIFY_ONLY, &user_can0_msgq);
```

```cpp
/**
 * @brief 阻塞等待发送消息，仅处理本次就绪的队列
 * @param context 未使用
 * @return Continue=本轮就绪队列处理结束
 */
static TaskResult Task(void* context)
{
	(void)context;

	for (auto& event : events_) {
		event.state = K_POLL_STATE_NOT_READY;
	}

	const int ret = k_poll(events_, 2, K_FOREVER);
	if (ret != 0) {
		DUST_LOG_ERR("can poll fail ret=%d", ret);
		return TaskResult::Continue;
	}

	if (events_[0].state == K_POLL_STATE_MSGQ_DATA_AVAILABLE) {
		SendPending(user_can1, &user_can1_msgq, "can1");
	}

	if (events_[1].state == K_POLL_STATE_MSGQ_DATA_AVAILABLE) {
		SendPending(user_can0, &user_can0_msgq, "can0");
	}

	return TaskResult::Continue;
}
```

两个判断分别检查自己的事件。只有一项就绪时不会调用另一条总线的处理函数；两项都就绪时才会依次处理两路。不能用一个笼统的“poll成功”代替事件来源判断。

另一条队列在处理期间才收到消息、但本次事件未报告就绪时，本轮不主动读取它；下一次 `k_poll()` 会识别队列非空并立即返回，不会丢失该消息。复位事件状态不等于清空队列。

线程仅保留一次启动：

```cpp
thread_.Start(Task, K_NO_WAIT, ThreadPrio::High, nullptr, "can");
```

`K_NO_WAIT` 取消框架额外的1 ms睡眠；任务内部仍通过 `k_poll(..., K_FOREVER)` 阻塞。原代码是非阻塞取队列后睡眠，这里明确改为消息驱动等待，不声称等待方式完全不变。

## 4. “保留逻辑”的实际限制

单线程不可能保留两个独立线程的全部调度时序。这里保留的是数据、每路FIFO和错误处理语义，必须明确以下变化：

1. **两路发送的线程等待会相互影响。** 原来 CAN1 在驱动中等待时，CAN0 线程仍可能运行；合并后 CAN0 需要等当前 CAN1 的 `Send()` 返回，反之亦然。
2. **事件选择只决定处理哪条队列，不能消除发送调用内的等待。** 两项同时就绪时，后处理的一路仍需等待前一路。
3. **等待方式改为消息驱动。** 框架周期改为 `K_NO_WAIT`，并由 `k_poll()` 阻塞；`Send(..., K_MSEC(1))` 的发送等待参数保留。二者不能混淆，不承诺严格 1 kHz。
4. **不添加本拍帧数上限或总耗时预算。** 原任务持续排空队列，本规划保留该语义；如果生产者持续补充消息，任务可能长时间不返回。各路容量16不能证明一拍最多只处理32帧，因为处理过程中还可能有新消息入队。
5. **不增加发送失败重试。** 当前失败消息已经从队列移除，合并后同样只记录失败并继续，不通过重新入队改变FIFO和失败行为。
6. **两路CAN硬件仍可独立收发。** 合并的是软件提交线程，不是把两条物理总线变成一条，也不等待反馈后才发送另一条总线。

如果实际业务必须保留“两路驱动等待互不影响”，则应保留原双线程，或另行授权设计发送调度；不能同时承诺严格保持该性质与合并成一个执行线程。

## 5. 修改清单与代码风格

后续获准实施时，在 `project/thread/can/trd_can_tx.cpp` 中：

1. 保留 `static Thread<> thread_{};`，删除 `thread_can0_`。
2. 保留 `user_can1`、`user_can0` 两个实例，不更名、不合并。
3. 在同一 namespace 内增加 `static void SendPending(...)`，保留原来的队列排空逻辑。
4. 增加两项队列事件及其初始化；`Task()` 使用 `k_poll()` 阻塞等待，逐项检查 state，仅调用就绪队列的 SendPending；移除 TaskCan0()。
5. `thread_start()` 仅保留一次 `thread_.Start(..., "can")`，周期改为 `K_NO_WAIT`，删除第二次 Start。
6. 仅在 `thread_init()` 中补队列事件初始化；原有 CAN 初始化、两个接收回调绑定、`REGISTER_INIT`、`REGISTER_THREAD` 保持原样。
7. 更新文件 brief、相关任务注释和版本说明，继续使用现有 `@brief/@param/@return` 中文注释形式，不批量翻译或重排其他代码。

保留既有制表符缩进、命名、函数大括号习惯、指定初始化器和日志宏。不为合并引入额外成员表、总线抽象层、全局变量或动态分配。

本项目 `project/Kconfig` 的 `TRD_CAN_TX` 另需增加一行 `select POLL`，以启用 Zephyr 的 `k_poll()` API，不修改公共 Kconfig。不修改 CMake、消息结构、队列容量、CAN驱动、控制线程、上位机、EtherCAT或公共子树。工作区当前已有的 IMU 改动与原规划文档不属于此次线程合并范围。

## 6. 内存收益

预期移除一份 `Thread<>` 对象及对应线程资源，减少一个任务的调度和统计开销。

默认请求栈大小为1024 B，但实际静态RAM变化还受到线程控制块、对象成员、保护和对齐影响；没有新旧ELF/map对比前，不给出确定的节省字节数。

这次合并**不减少**每路 `hpm_mcan_data` 驱动对象，也不缩小 AHB_SRAM 中的 CAN 消息RAM。此前记录的13,656 B驱动对象和20 KiB消息RAM问题仍然独立保留。

## 7. 验证与放行条件

实施后的必要检查分开进行；本次规划不执行：

| 项目 | 预期结果 |
| --- | --- |
| 两路均为空 | 阻塞在k_poll，不循环空转，不调用Send |
| 任意一路从空变为有消息 | 唤醒同一发送线程，无额外1 ms周期等待 |
| 消息在排空和下次poll之间到达 | 不丢唤醒，下次poll识别当前队列非空 |
| 仅CAN0有多帧 | 顺序、ID、DLC、payload与原CAN0一致，持续处理到暂无消息 |
| 仅CAN1有多帧 | 与原CAN1一致；CAN0未就绪则不读取、不发送 |
| 只有CAN0事件就绪 | 只处理CAN0，不读取CAN1队列，不调用CAN1发送 |
| 两项同时就绪 | 两个事件分别命中，顺序处理两条队列，保持各自FIFO |
| 某一路发送等待较长 | 明确测量另一条队列新增的等待，不能只测正常空载 |
| CAN接收 | 两个原接收回调继续独立工作，不因删除TaskCan0而丢掉CAN0反馈 |
| 初始化失败 | 设备检查、初始化顺序和原失败返回行为不变 |
| 线程列表 | 仅剩名称can的一个发送线程，can0线程消失 |
| 内存 | 比较相同配置的新旧ELF/map，只归因于线程资源，不混入CAN容量调整 |

将来如需验证，优先使用替身队列/发送接口检查上述队列和失败语义，再按用户授权做目标编译与实机收发。不得因规划写了验收项就自行构建、运行或发送CAN。

## 8. 结论

推荐的最小方案是：在原文件中保留一个线程，通过 `k_poll()` 阻塞等待两条独立FIFO，唤醒后根据各自事件状态，只处理就绪队列，沿用原组帧、timeout和失败处理。实施前应接受单线程带来的跨总线等待耦合；若该耦合不可接受，则保持原双线程，不以“合并”名义偷偷重设计发送机制。
