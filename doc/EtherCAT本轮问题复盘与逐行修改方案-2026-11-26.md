# EtherCAT 本轮问题复盘与逐行修改方案

日期：2026-11-26
范围：从站 `zephyr_user` EtherCAT 协议栈/HPM HAL、当前从站 PDO v2 业务线程、SOEM 主站，以及本轮调试操作。本文把日志确认的事实与需要板上复测的事项分开；行号对应本文记录时的工作树。

## 当前结论

最新主站日志停在 PREOP 请求，尚未进入 PDO 状态。请求记录中 AL Control 回读为 `0x0011`、当次 AL Status 为 `0x0001`（INIT）；随后 CoE 探测记录 AL Status=`0x0011`（INIT 加错误位）且 `SDO read 0x1C00:0 ret=0`。这说明 SDO/PDO 失败发生在从站没有进入 PREOP 之后，不能据此认定 CoE 字典或 v2 PDO 字段布局错误。

同一轮从站日志每秒报告 `PDI_ISR_total=0`、`polls=0`、`AL=0`，但 EtherCAT 站地址从 `0x0000` 变为 `0x1001`。这里的 `polls` 是该秒内采到非零 AL Event 的样本数，不是 `Poll()` 线程调用次数；因此它表示协议层没有观察到 AL Event。帧已到 ESC，但此前把事件处理改成 ISR-only，而 PDI ISR 实际没有触发，是这次 PREOP/PDO 回归的直接原因。

## 已确认的问题与逐行处理方式

### 1. 把 AL Event 改成 ISR-only，实际 PDI ISR 却没有运行

证据：从站日志连续约 40 秒为 `PDI_ISR_total=0 polls=0`（`polls` 为非零事件样本数）；主站已经发现从站、分配站地址，但 PREOP 请求后仍处于 INIT，随后 CoE 探测读到 `AL Status=0x0011`，SDO 失败。此时没有 PDO 往返是状态机尚未到 PDO 阶段的结果。

相关协议栈位置：

- `E:/Zephyr/zephyr_user/midlayer/ethercat/core/ecat_device.cpp:181-216`：`EcatDevice::Poll()`。记录的原始路径在第 195 行从 `0x0220` 读 AL Event 并调用 `HandleAlEvents()`。
- `E:/Zephyr/zephyr_user/midlayer/ethercat/core/ecat_device.cpp:248-257`：`EcatDevice::OnPdi()`。PDI ISR 也读取 AL Event 并直接调用 `HandleAlEvents()`。
- `E:/Zephyr/zephyr_user/zephyr/drivers/ethercat/hal/hpm/ecat_hal_hpm.cpp:273-276`：注册 PDI/SYNC/RESET 回调；第 364-375 行启动 ESC 中断。
- 本轮曾试验把 `Poll()` 的事件来源改为 ISR 锁存队列，并停用 Poll 的硬件事件读取。实测 `PDI_ISR_total=0`，所以该版本没有 AL Control/邮箱/SM 事件可处理。

修正方式：先恢复可运行路径，不能在 PDI ISR 未验证前删除 Poll 兜底。调试时必须明确只让一个路径消费 read-to-clear 的 `0x0220`：

1. 若临时采用 Poll 模式：由 `Poll()` 读取 AL Event 并调用 `HandleAlEvents()`；PDI 路径不得再并发读取/处理同一事件，必要时屏蔽 PDI 事件源，但保留独立 SYNC/RESET 所需中断。
2. 若切到 SSC 风格 PDI 模式：先修好 IRQ 路由，确认真实 AL Control 和 SM2 流量期间 `PDI_ISR_total` 增长；由 ISR 读取并锁存事件，线程消费队列，然后才移除 Poll 的 `ReadAlEvent()`。

不能只切换到第 2 种模式而不验证中断计数。

### 2. 诊断代码也读取了 read-to-clear 的 AL Event

`EcatDevice::Poll()` 在 `ecat_device.cpp:195` 读一次 AL Event，`OnPdi()` 在第 256 行又读一次；`CaptureDiagnosticSnapshot()` 在第 1298 行仍执行 `sample.events = esc_->ReadAlEvent()`。`Poll()` 随后在第 214 行调用 `CaptureDiagnosticSnapshot()`。因此诊断采样也是第三个事件消费者，可能把协议处理路径还没读到的事件清掉。

修正方式：删除诊断快照对 ESC `0x0220` 的直接读取，记录事件拥有者已经读出的缓存值（例如 `last_events_`）；只有选定的 Poll 或 PDI ISR 事件拥有者可以读清该寄存器。诊断不能改变协议状态或消费事件。

### 3. 主站本地副本的期望 WKC 少算一个输出系数

文件：`temp/Dust_Linux_Architecture-main (1)/Dust_Linux_Architecture-main/framework/drivers/communication/ethercat/ecat.hpp:785-797`。第 790-791 行把输出和输入各加 1；SOEM 的标准期望值是 `outputsWKC * 2 + inputsWKC`。单从站双向 PDO 时，当前算法给出 2，正确值为 3。此前日志确实出现 `expected WKC=2 (outWKC=1 inWKC=1)`。

应改为：

```cpp
pdo_.expected_wkc = ctx->grouplist[0].outputsWKC * 2U
                  + ctx->grouplist[0].inputsWKC;
```

这会造成 WKC 判定/诊断不准确，但不是最新日志停在 INIT、PREOP 失败的直接原因。注意：`temp/Dust_Linux_Architecture-main (1)` 是本地副本；此前已推送的主站版本有单独修正提交 `f27d134`，不要用这个旧副本覆盖已修正主站。

### 4. 主站副本无条件设置 AL Control 的 ACK 位

同一主站副本 `ecat.hpp:841-844`，第 843 行把每个请求都写成 `state | kAlStatusErrorBit`。这里的 `0x0010` 是 AL Control 的错误确认位，应仅在请求前读到 AL Status 的错误位时设置；无错误请求不应无条件带 ACK。较新的主站修正是“仅在错误位存在时确认”，本地 `temp` 副本仍保留旧实现。

修正方式：请求前读取 AL Status；先令 `request = state`，且仅当 `raw_al_status & 0x0010` 非零时令 `request |= 0x0010`，再写 AL Control。日志中的 AL Control 写回值和 AL Status 必须分开标注，不能把寄存器回读值当作当前 AL 状态。已推送主站仓库的 `91d8696` 修正了“仅在有错误时 ACK”；本地 `temp` 副本仍是旧代码。

### 5. CoE/SDO 失败是 PREOP 未到达后的下游表现

最新主站日志显示 PREOP 请求当次 `alstat=0x0001`，随后 CoE 探测为 `alstat=0x0011`、`SDO read 0x1C00:0 ret=0`、`readPDOmap ret=0`。之前的日志中，同一从站在 PREOP 下可以 `SDO read 0x1C00:0 ret=1` 且 `readPDOmap ret=1`，映射为双向各 256 B。因此应先恢复 AL Event/状态机推进，再评估 CoE；不能把这次 SDO 失败单独归因于 SDO 实现。

### 6. PDRAM 探针“函数返回”不等于数据已正确读写

从站此前报告 `pdram read probe=0`、写入后回读仍为 `0`，并报告 verify mismatch；后续 trace 只证明 `hpm_esc_write()` 调用返回（`HAL PDRAM block write raw end`），不能证明 ESC 中的 0x1400 内容等于期望值。

当前 HPM HAL 原始版本位置：`E:/Zephyr/zephyr_user/zephyr/drivers/ethercat/hal/hpm/ecat_hal_hpm.cpp:399-437` 的读路径对齐访问使用 `hpm_esc_read_block()`；第 445-453 行对齐写直接使用 `hpm_esc_write()`。如重新定位 PDRAM 问题，需要记录同一地址的写前值、写后 ESC 读回值及主站收到的 SM3 字节；不能仅以 begin/end 日志判定成功。启动 `0x1400` 初值为 0 本身也不能单独证明 PDRAM 不可访问。

## PDO v2 布局核对

当前从站布局定义在 `project/thread/ecat/pdo_layout.hpp:19-30, 106-142`：

- 线上 SM2/RxPDO 与 SM3/TxPDO 都是 256 B；从站结构体都补齐到 256 B。
- 从站发往主站的有效前缀 156 B：反馈头 30 B，遥控偏移 30、28 B，IMU 偏移 58、50 B，4 个电机反馈从偏移 108 开始、共 48 B；剩余 100 B 为零。
- 主站发往从站的有效前缀 44 B：命令头 36 B，`motor_command[8]` 偏移 36；剩余 212 B 为零。
- 主站的 `pdo_layout.hpp` 定义 packed 有效结构体分别为 156 B 和 44 B；主站日志/SM 配置仍是每个方向 256 B。这是“有效字段前缀 + 256 B 线上映射”，并非方向或长度相反。

从站周期线程 `project/thread/ecat/trd_ecat.cpp:260-291` 每 1 ms 调 `slave_.Poll()`，然后在短暂 `irq_lock()` 内 `SetInputs()` / `Outputs()`；这与已知旧线程的收发骨架相同。当前主站协议字段布局与从站 `pdo_layout.hpp` 的偏移、魔数和 slot map version 2 对齐。

不能把旧快照的业务结构原样覆盖到 v2：旧快照 `temp/Dust_Sentinel_Robot_2027-3bf982e5981e726858f31dbe975ba31879cd74b8/project/thread/ecat/trd_ecat.hpp:20-32` 用两个 `uint32_t[64]` 占位；对应 `.cpp` 把 `StatusPacket` 和 `CmdVelPacket` 放在 PDO 偏移 0。当前主站偏移 0 要求分别是 `PDB1` 反馈头和 `CMC1` 命令头。只保持 256 B 长度而照搬旧 payload，会出现“长度相同、内容完全错位”。

此外，该旧快照的 `project/CMakeLists.txt:12-15` 将 framework/midlayer/Zephyr 底层指向外部 `../../../zephyr_user`。快照并不包含协议栈或 HPM HAL，故不能从它直接覆盖 `EcatDevice`、PDI ISR 或 ESC 访问实现；它也没有固定配套的 `zephyr_user` commit。

当前从站 `DecodeCommand()` 在 `project/thread/ecat/trd_ecat.cpp:197-219` 检查 magic、长度、slot map、boot echo，但没有检查 `proto_major/minor`。这不是本轮 PREOP 故障的原因；要完整执行主站 v2 协议拒收规则，应补上版本检查，并用主站文档中的异常帧逐项验证。

## 日志与状态的正确解读

- `station=0x1001` 只证明 ESC 收到并执行了主站配置站地址访问，不证明 AL 事件已由协议栈处理，也不证明 PDO 字节内容正确。
- CoE 探测记录中的 `AL Status=0x0011` 表示 INIT 加错误位；此状态下 SDO/readPDOmap 失败是后果。请求日志中的 `alctl=0x0011` 是 AL Control 回读，不能与同一行 `alstat=0x0001` 混为一谈。先看 AL Status Code 和 `AL Control → HandleAlEvents → Publish` 链路。
- CoE/SDO 在旧日志里成功、当前 INIT 错误下失败，不能据此认定 SDO 代码退化。
- SM2/SM3 读回 256 B 和主站 WKC=3 可证明映射/过程数据事务至少有响应；只有比较实际 0x1100/0x1400 payload，才能证明数据语义收发正确。
- 主站在 OP 请求等待期间需要持续发送 cyclic PDO；从站 `EnterOp()` 在 `ecat_device.cpp:869-881` 若尚无首个输出帧会返回 `kAlStatusInWork`。主站 `ecat.hpp:891-906` 仅在目标为 OP 时发送过程数据，这是有意行为；此前 SAFEOP wait 日志中的 `cyclic_pdo=off` 本身不是错误。

## 建议的验证顺序

1. 用单一 AL Event 所有者构建从站；若用 Poll，日志应能看到 AL Control/邮箱/SM 事件，状态可到 PREOP；若用 PDI ISR，必须先看到 `PDI_ISR_total` 增长，再切线程消费队列。
2. PREOP 成功后确认 SDO `0x1C00:0` 与 `readPDOmap` 返回成功。
3. SAFEOP 时确认 SM2=`0x1100/256`、SM3=`0x1400/256`，输入帧从偏移 0 开始出现 `PDB1`，输出帧偏移 0 为 `CMC1`。
4. 主站进入 OP 时保持 cyclic PDO；从站首次 SM2 事件和 `Sm2Count` 增长后确认 OP。
5. 分别比对主站 TxPDO 前 156 B 与从站生成数据、主站 RxPDO 前 44 B 与从站 `Outputs()`；确认 padding 为零，并核对 WKC 期望值为 3。
