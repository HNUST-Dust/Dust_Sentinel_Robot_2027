# 为什么那个问题没有在当前工作区暴露

日期：2026-11-26
问题：本次会话花费最多时间的故障——**进 SAFE-OP 时卡死 / SM 配置被写坏 / 站地址变 0 / 反复 0x0011**——在当前回退后的工作区里没有出现。
本文对比版本差异，说明它为什么被“挡在前面”的缺陷掩盖。

## 1 结论

当前工作区（sentinel `6424ed7` + zephyr_user `fbe8d2b` + midlayer `eb289d1`）**走不到 SAFE-OP 那段代码**：

1. midlayer `eb289d1` 缺少 `8dab046` 的三项 CoE 修复，主站在 `readPDOmap` 阶段就反复失败，根本走不到请求 SAFE-OP；
2. 即使 CoE 偶然通过，`eb289d1` 的 `CheckSmSettings` 仍然严格要求 SM 使能位，SM 状态稍有异常就直接返回 `0x0016/0x001D`，**不会进入 `EnterSafeOp`**；
3. 本次会话我们在 8dab046 之上打的补丁（INIT 逐级退出、ISR/线程串行、HAL 锁、PDRAM 32 位写）在当前工作区一个都不存在。

HAL（`fbe8d2b`）与调试时（`75b5f2b`）**逐字节相同**，所以 PDRAM 卡死的“能力”两个版本都有；差别只在于能否走到那一步。

## 2 版本基线

| 层 | 当前 | 本次调试时 | 差异 |
|---|---|---|---|
| sentinel | `6424ed7`（18:12） | `279bece`（22:23）+ 会话改动 | PDO 旧布局、无 chassis/can_tx |
| zephyr_user | `fbe8d2b`（18:12） | `75b5f2b`（22:23） | **只有 midlayer 指针不同**，HAL 文件逐字节相同 |
| midlayer | `eb289d1`（11-12） | `8dab046`（22:23）+ 会话改动 | 见下 |

`git diff eb289d1 8dab046`：6 个文件，113 增 37 删。

## 3 逐项差异与失败链

### 3.1 midlayer `eb289d1` 缺失的（导致 CoE 阶段失败）

| 缺陷 | 位置 | 现象 |
|---|---|---|
| AL 回 INIT 不停邮箱、不发布 INIT | `ecat_device.cpp` `ExecuteAlStep` → `AlAction::BackToInit` 只做 `BackToInit(); SetState(Init);` | 主站重连后邮箱写计数器不复位，第一条 SDO 被当重传丢弃 |
| INIT/BOOT 下拒绝所有 SDO | `ecat_dictionary.cpp` `AllowedInCurrentState` 的 `default: return false;` | 主站切 PREOP 同一拍读 0x1C00 被拒 |
| 连续 SDO 不补取 | `ecat_mailbox.cpp` `Service()` 无 `receive_locked_` 补取 | 第二条 SDO 在 `send_full_` 期间被静默丢弃 |
| SII 只回 4 字节 | `ecat_sii_service.cpp` `HandleRead` 按 `read_width_` | SII 偶发把邮箱信息读成 0 |

结果：`readPDOmap ret=0` 无限重试（会话早期的原始现象），主站不会请求 SAFE-OP。**PDRAM 代码路径不可达。**

### 3.2 midlayer `8dab046` 放宽的（正是它把栈送进 SAFE-OP）

`CheckSmSettings` 在 `8dab046` 里去掉了四处 `IsEnabled()` 判断（SM0/SM1 的 `if (!mbx_out.IsEnabled())`，SM2/SM3 的 `if (enabled && length == 0)` / `else if (length != 0 || layout.rx_size != 0)`）。

- `eb289d1`：使能位不对时**在校验阶段就拒绝**（返回 `0x0016` 或 `0x001D`），不会执行 `EnterSafeOp`；
- `8dab046`：跳过使能检查，即使 SM 状态不完美也继续进入 `EnterSafeOp` → 使能 SM2/SM3 → `PublishInputs` 写 0x1400 → 才暴露 PDRAM 卡死。

所以“卡死”是 8dab046 放宽校验后**新放行出来**的路径，不是新引入的代码。

### 3.3 本次会话的补丁（当前工作区完全没有）

| 补丁 | 作用 |
|---|---|
| INIT 逐级退出 + `Publish()` | 修 3.1 的第一条，让 CoE 能稳定 |
| `OnPdi` 只暂存事件、`Poll` 统一处理 | 修 ISR/线程并发导致的 `0x0011` |
| `EnableSyncManagerChannel` 只写 0x0807 | 修 SM 控制字节被写坏（`0x01013000` → `0x001D`） |
| HAL：ESC 访问 `k_spinlock` | 修寄存器间歇读 0（站地址、ALSTAT、SM 控制字节） |
| HAL：1 字节写直通、PDRAM 32 位字写 | 修 `publish inputs` 卡死 |
| 转换成功清错误锁存 | 防止错误位常挂、主站反复带 ACK |

这些补丁既不在 `eb289d1`，也不在 `8dab046`，回退后就全部消失。

## 4 为什么现象看起来“消失了”

| 现象 | 依赖条件 | `eb289d1` |
|---|---|---|
| `readPDOmap ret=0` 循环 | 3.1 的缺陷 | **有**，最先出现 |
| `sm check fail ... 0x001d` | 进入 SAFE-OP 校验 | 校验更严格，**更早拒绝** |
| `publish inputs begin` 后卡死 | 通过校验并进入 `EnterSafeOp` | 被前两步挡住 |
| `station ... -> 0x0000` | 到达 SAFE-OP 后 ESC 行为 | 到不了 |
| `al_state 0x08 failed code=0x0011` | AL 事件并发 + 主站不等 SAFE-OP | 到不了 OP 请求 |

也就是说：当前工作区不是“没有这个问题”，而是**在更早的阶段就失败了**，把后面的问题全部掩盖。

## 5 反向验证方法

在 `eb289d1` 上仅加诊断（不改逻辑），跑一次同款上位机：

1. 在 `EcatDevice::EnterSafeOp()` 第一步加日志 `safeop enter`；
2. 在 `EnableSyncManagerChannel` 前后加日志；
3. 在 `EcatProcessData::PublishInputs` 前后加日志。

判读：

- 只看到 `readPDOmap ret=0`、没有 `safeop enter` → 确认被 CoE 阶段挡住；
- 出现 `safeop enter` 但没有 `publish end` → PDRAM 卡死复现，说明 HAL 是共同根因；
- 出现 `sm check fail` → 被使能校验挡住，符合 3.2。

## 6 结论与风险

- 结论：问题没有消失，只是被 `eb289d1` 的早期缺陷挡住了。修复必须按《EtherCAT 协议栈修复规划-2026-11-26》的阶段 1→4 顺序推进，否则每修好一层就会“冒出”下一层的旧问题。
- 风险：HAL 在三个版本里完全相同，PDRAM 32 位访问与 ESC 访问加锁这两个修复必须补上，否则一旦 SAFE-OP 校验通过就会立刻复现卡死。
