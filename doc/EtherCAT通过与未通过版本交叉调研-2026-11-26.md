## 1. 核心判断

**不能把这次退化概括成“PDO 改紧凑后长度不一致，所以最后连 PDO 都过不了”。未通过版主从业务前缀是配套的，从站两方向仍为 256 B；现有证据支持的解释，是调度缺陷、状态切换时序和后续事件处理改动叠加，使故障扩散到了建链层。各次历史失败的具体贡献仍需按证据等级区分。**

本次确认了五件关键事实：

1. **未通过从站有明确的 CAN 队列空转缺陷。** `SendPending()` 被注释，但 CAN 线程以 `K_NO_WAIT` 周期运行；ECAT 每拍仍往队列写消息。第一条消息入队以后，`k_poll(K_FOREVER)` 因队列一直非空而立即返回，线程持续空转，同优先级的 ECAT 主循环受到时间片调度延迟。电机发送调用本身也不会执行。
2. **两个主站目录的 EtherCAT 驱动完全相同，都保留了容易误导调试的时序。** 独立 `readPDOmap` 探测在 `config_init` 后立即调用，未先确认 PREOP；`config_map` 后则直接请求 OP，没有显式确认 SAFEOP。前者能造成“诊断 CoE 失败但后面的正式映射成功”，后者能触发 `0x0011`。
3. **已有复盘记载了另一轮直接回归：改为 ISR-only 后，PDI ISR 实际没有运行，Poll 读取事件的路径又被撤掉，导致停在 INIT。** 这能解释“后来 SDO/PDO 都失败”，但这份修改没有保存在本次给定的 22:23 快照，必须与快照缺陷分开归档。
4. **当前所谓通过版实际是 256 B 图案收发基线。** 主站发 `00 01 ... FF`，从站不校验命令头就更新会话字段；它证明链路与数据搬运，不能证明 v2 会话、C620 转发和底盘闭环已经通过。
5. **SII 有确定的格式错误，不能再只写成“旧镜像以后更新”。** 当前与失败快照的 SM2/SM3 默认长度都已是 256 B，但 PDO 类别把每个应为 8 B 的 SII Entry 写成了 4 B。CoE 正常时可绕开这个缺陷；走 SII 回退时会算出错误长度。这是共有缺陷，不足以单独解释为什么两版表现不同。

因此，“越改越查”的主要问题是：**把业务数据错误、周期调度退化、PREOP/SAFEOP 尚未完成、SII 回退错误，以及调试过程中新引入的事件停摆，当成了同一种 PDO 故障处理；再用权限放宽、固定长度和访问方式修改去追下游现象，失去了单变量对照。**

## 3. 通过版与未通过版的 PDO 到底有没有对不上

### 3.1 实际布局

方向统一按主站视角：Inputs 为从站上传，Outputs 为主站下发。

| 项 | 当前通过版主从 | 未通过主站 | 未通过从站 |
|---|---|---|---|
| 线上 SM2 / SM3 | 256 / 256 B | 由在线映射决定，预期 256 / 256 B | 256 / 256 B |
| `slot_map_version` | 1 | 2 | 2 |
| 反馈头 | 34 B | 30 B | 30 B |
| 遥控起点/长度 | 34 / 28 B | 30 / 28 B | 30 / 28 B |
| IMU 起点/长度 | 62 / 50 B | 58 / 50 B | 58 / 50 B |
| 电机反馈 | 无，112 以后填零 | 108 起、4×12 B | 108 起、4×12 B |
| 上传 C++ 结构长度 | 256 B | 156 B | 256 B，其中后 100 B reserved |
| 命令头类型长度 | 38 B，但下行实际是图案数组 | 36 B | 36 B |
| 电机命令 | 不使用 | 36 起、8 B | 36 起、8 B |
| 下发 C++ 结构长度 | 256 B | 44 B | 256 B，其中后 212 B reserved |

源码：[当前从站布局](../project/thread/ecat/pdo_layout.hpp#L19)、[通过主站布局](../temp/主站通过版/project/thread/ethercat/pdo_layout.hpp#L24)、[未通过主站布局](../temp/主站为通过版/project/thread/ethercat/pdo_layout.hpp#L24)、[未通过从站布局](../temp/从站未通过版/project/thread/ecat/pdo_layout.hpp#L19)。

未通过主站只复制 44 B 输出、156 B 输入；IOmap 在建图时清零，SOEM 仍按在线映射发送完整过程数据。两方向小结构本身不会把从站 `sizeof(PdoInputs/PdoOutputs)` 改小，也不会自动把 SM 改为 44/156 B。

此外驱动的长度检查是 `映射长度 >= sizeof(结构)`，而非相等。因此这种“主站有效前缀、从站整帧补齐”的写法能工作，但也可能掩盖错误的大映射，必须看实际在线长度。[主站 Send/Read 检查](../temp/主站通过版/framework/drivers/communication/ethercat/ecat.hpp#L112)

**结论：M-fail 与 S-fail 的有效字段布局匹配；没有证据表明紧凑前缀本身造成 `readPDOmap ret=0` 或 PREOP 失败。**

### 3.2 从站在线映射为何一直应为 256 B

[PdoProfile](E:/Zephyr/zephyr_user/zephyr/contract/ecat_profile.hpp#L30) 由 `sizeof(T)` 得到字节数和 32 位字数。S-pass/S-fail 两方向结构都是 256 B，因此各自是 64 个 32 bit 条目。

[过程数据 Configure](E:/Zephyr/zephyr_user/midlayer/ethercat/core/pdo/ecat_process_data.cpp#L59) 累加映射位长，结果为每方向 `64×32=2048 bit=256 B`。业务头内多几个字段、少几个 reserved，不会改变这个总长，只要整帧仍补齐 256 B。

这与用户给出的 CoE 实测摘要一致，但摘要不是本次重新测得的数据。

### 3.3 当前通过版通过到什么程度

[M-pass UpdateCommand](../temp/主站通过版/project/thread/ethercat/trd_ethercat.cpp#L126) 完全按 `data[i]=i` 填充 256 B。[S-pass DecodeCommand](../project/thread/ecat/trd_ecat.cpp#L182) 逐字节核对图案，随后只要有新 SM2 且 OP，就从图案里取 `host_session`、`command_seq`，没有验证 magic、length、slot map 或 boot echo。

将图案按当前 packed 命令头解码会得到：

```text
magic            = 0x03020100       // 不是 CMC1
byte_length      = 0x0908           // 不是 256
slot_map_version = 0x0B0A           // 不是 1 或 2
host_session     = 0x0D0C = 3340    // 不是主站建立的 session 1
command_seq      = 0x11100F0E
```

所以旧记录中的“session 1 accepted”“motor command active”属于其他历史阶段，不能与当前图案版本视作同一次验收。**现有通过结论应限定为：OP 和 256 B 图案/反馈收发基线已通过；正式命令协议与电机链路另行验收。**

当前 `kSlotMapVersion=1` 的布局还从历史 40/32/56 B 变成了 34/28/50 B，但版本值未变。它与旧 v1 并不保持字节兼容；同长度、同 magic、同 slot map 值不足以保证解码正确。这是后续恢复业务时必须处理的版本管理问题，无法解释早于 PDO 解析的 INIT/PREOP 故障。

## 4. 未通过从站最具体的新增问题：CAN 队列空转

### 4.1 缺陷形成完整闭环

证据链：

1. [S-fail Kconfig](../temp/从站未通过版/project/Kconfig#L84) 由 ECAT 选择 chassis 和 `TRD_CAN_TX`。
2. [ECAT Task](../temp/从站未通过版/project/thread/ecat/trd_ecat.cpp#L286) 每拍调用 `PublishMotorCommand(outputs)`。
3. [PublishMotorCommand](../temp/从站未通过版/project/thread/ecat/trd_ecat.cpp#L226) 即使会话无效、未到 OP，也会构造零电流消息并 `k_msgq_put(..., K_NO_WAIT)`。
4. [CAN Task](../temp/从站未通过版/project/thread/can/trd_can_tx.cpp#L76) 等待 `k_poll(..., K_FOREVER)`，但第 93 行真正消费队列的 `SendPending(channels_[i])` 被注释。
5. [CAN 启动](../temp/从站未通过版/project/thread/can/trd_can_tx.cpp#L149) 使用 `K_NO_WAIT` 周期、`ThreadPrio::High`。
6. [线程外壳](E:/Zephyr/zephyr_user/framework/init/thread/thread.hpp#L391) 在周期为 `K_NO_WAIT` 时没有 sleep，也没有额外 yield。
7. [Zephyr k_poll 实现](E:/Zephyr/zephyr/kernel/poll.c#L283) 对已就绪事件直接返回；重设 `event.state` 不会把消息队列中的消息取走。

于是第一条消息进入 CAN1 队列后：

```text
队列非空
→ k_poll 立即返回
→ 不调用 SendPending，不取消息
→ Task 返回 Continue
→ 外壳无等待立即再调 Task
→ 队列仍非空，继续立即返回
```

这个问题在已提交的 `279bece` 中也存在，不只是临时未提交状态。队列深度为 16，后续写满后的 `k_msgq_put` 返回错误也被忽略。[队列定义](E:/Zephyr/zephyr_user/framework/topic/to_can_tx/to_can_tx.cpp#L17)

### 4.2 为什么它会干扰 CoE/PDO 排查

CAN 与 ECAT 都是优先级 3。当前已有 `.config` 的时间片为 20 ms，Zephyr 默认也是 20 ms；ECAT 本来每拍 `k_sleep(1 ms)`，唤醒以后面对同优先级持续 ready 的 CAN 线程，不能假定立刻执行。[时间片配置](../project/build/zephyr/.config#L67)、[优先级](E:/Zephyr/zephyr_user/framework/init/thread/thread.hpp#L24)

这会造成：

- CAN 实际发送函数不执行，足以直接解释“电机命令没有送出”。
- ECAT `Poll()`、邮箱 CoE 请求分发、SII 软件应答和业务反馈刷新受到同优先级时间片延迟，1 ms 周期承诺失效。
- [EcatDevice::Poll](E:/Zephyr/zephyr_user/midlayer/ethercat/core/ecat_device.cpp#L162) 中接收 SDO、生成响应和发送队列推进跨越多拍，延迟可能累计，进而增加主站超时和时序竞争概率。
- ESC 自己的帧转发/FMMU 事务仍可能有 WKC，ISR 也不等于全部被阻塞，所以会出现“链路/WKC 有响应，但软件服务迟滞”的组合。

**证据边界：忙循环及不发送是源码确定事实；具体是哪条 SDO 因它超时、当时最长延迟多少，缺少该失败固件的运行统计。不能写成‘一定永久饿死 ECAT’：同优先级时间片仍可能让 ECAT 获得 CPU。**

与之对照，S-pass 移除了 CAN/chassis 线程，也不再每拍发布 CAN 消息。因此它同时撤除了这项明确的调度干扰，不能只把恢复通过归功于 PDO 布局回退。

## 5. 主站时序：为什么诊断显示 CoE 失败，后面仍可能进 OP

### 5.1 两份主站驱动的实际调用链

[共同驱动](../temp/主站通过版/framework/drivers/communication/ethercat/ecat.hpp#L95)：

```text
Open
→ Discover: ecx_config_init
→ Enumerate: ecx_readstate
→ ConfigureSlaves: 仅回读 SM 长度
→ ConfigurePdo:
    独立 ecx_readPDOmap 探测       ← 没显式等 PREOP
    ecx_config_map_group         ← SOEM 正式建图
    按 SOEM 结果重写 SM2/SM3 长度
→ ConfigureDc
→ RequestOperational: 直接请求 OP ← 没显式等 SAFEOP
```

这两份快照里没有旧主站调试文档所述的邮箱字段兜底、PREOP 主动等待、SAFEOP 主动等待或站地址自动恢复。它们属于历史改动记录，不能当作这两份文件的实际实现。

### 5.2 独立 readPDOmap 是有副作用的主动探测

上游 SOEM `ecx_config_init` 尾部会请求 PREOP，但不代表从站软件已经处理完成。正式映射路径 `ecx_map_coe_soe` 会先调用 `ecx_statecheck(PRE_OP)`，然后再读 CoE；直接调用 `ecx_readPDOmap` 则没有这个状态等待。

官方源码对照：[SOEM ec_config.c](https://github.com/OpenEtherCATsociety/SOEM/blob/49fc34923b973c17700592319159af22157350c9/src/ec_config.c#L470)、[正式映射前的 PREOP 检查](https://github.com/OpenEtherCATsociety/SOEM/blob/49fc34923b973c17700592319159af22157350c9/src/ec_config.c#L521)、[readPDOmap](https://github.com/OpenEtherCATsociety/SOEM/blob/49fc34923b973c17700592319159af22157350c9/src/ec_coe.c#L913)。

当前从站 INIT/BOOT 下拒绝 SDO，邮箱也要进入 PREOP 才启动。因此：

```text
config_init 发 PREOP 请求
→ 独立诊断抢先发 SDO
→ 从站尚在 INIT，诊断 ret=0
→ 后续 config_map 等 PREOP 后正式读 CoE
→ 正式映射仍可能成功并得到 256 B/方向
```

快照中的独立 `pdo_ret` 只打印，不作为失败条件；诊断 ret=0 后仍继续 `config_map_group`。这说明单看这行日志不足以判断最终 PDO 映射失败。[探测与正式建图](../temp/主站通过版/framework/drivers/communication/ethercat/ecat.hpp#L598)

用户摘要及 sentinel `5df10b9` 的提交说明都记载“SDO 诊断后移到 PREOP 后即通”，与上述机制一致。**但本次 M-pass 文件中该探测仍位于等待前，未保存这项修改。** 应把“实测后移成功”和“目录内代码仍是原顺序”分别记录。

上游 `readPDOmap` 返回的长度是 bit。`2048 B` 这行日志实际应理解为 `2048 bit=256 B`。此外上游 ret=1 只要求至少一方向找到非零位数，不等于两个方向长度均正确；必须同时核对 out/in 数值。

### 5.3 SAFEOP 未确认就请求 OP

[RequestOperational](../temp/主站通过版/framework/drivers/communication/ethercat/ecat.hpp#L793) 直接 `RequestState(OP)`。上游 `config_map_group` 请求 SAFEOP 后返回，上层紧接着写 OP；若从站还停留 PREOP，则 [Transition](E:/Zephyr/zephyr_user/midlayer/ethercat/core/ecat_device.cpp#L590) 明确返回非法状态跳转。

所以 `0x0011` 与“PDO 有效字段偏移错误”是两类问题。CAN 空转使状态处理延迟增大，会扩大这类竞争窗口，但不能仅凭代码确定某次 `0x0011` 一定由 CAN 引起。

当前驱动在 OP 等待中确实持续 `send_processdata/receive_processdata`，不能再写成“等进 OP 后才发首帧 PDO”。[RequestState 等待循环](../temp/主站通过版/framework/drivers/communication/ethercat/ecat.hpp#L748)

### 5.4 关于 SOEM 版本的限制

两份主站使用 `find_path/find_library` 链接系统安装的 SOEM，未保存实际 Linux 机器的库提交号和二进制。[依赖查找](../temp/主站通过版/framework/drivers/CMakeLists.txt#L21)

本次只读取 SOEM 官方仓库，固定参考提交 `49fc34923b973c17700592319159af22157350c9`。它用于验证函数行为与格式，不证明当时 Linux 运行的库恰好就是这个提交。上游内容未写入工作区，也未运行其代码。

### 6.2 确定的格式错误

标准 SII PDO 类别与 CoE 的 PDO mapping 条目格式不同。SOEM 的 [ecx_siiPDO](https://github.com/OpenEtherCATsociety/SOEM/blob/49fc34923b973c17700592319159af22157350c9/src/ec_main.c#L849) 按每项 8 B 解析；CoE mapping 的 32 bit 值不能直接拼成 SII Entry。

本镜像：

```text
Category 50 @ byte 0x162: length = 132 words = 264 B
PDO header: 8 B，宣称 64 entries
剩余 256 B → 每项实际仅 4 B

Category 51 @ byte 0x26E: 同样 264 B、64 entries、4 B/entry
```

64 个合法 SII Entry 应需要 `8+64×8=520 B=260 words`。当前类别却只有 132 words。

例如输入第一个条目被写成：

```text
00 60 01 20
```

上游按 8 B Entry 读取时，取第 6 个字节为 bit length，于是读到下一个短条目里的 `0x60`，并非期望 `0x20`。随后游标穿过类别边界，继续把后续类别当条目。

只按官方解析器的 64 次条目步长静态计算，在该镜像中会得到：

| 类别 | 错误位数合计 | 向上取整字节数 |
|---|---:|---:|
| TxPDO / 50 | 6566 bit | 821 B |
| RxPDO / 51 | 10979 bit | 1373 B |

这些是静态复算值，不是当时主站实测日志；具体旧 SOEM、SII 缓存或前序读取异常可能表现不同。因此历史记录中的“退成 1 B”不能直接归因于这一个格式错误，但这份镜像不能正确提供标准 SII PDO 回退映射是确定的。

Git `5622a67` 的差异还证明：前一版 1 项 PDO 使用 8 B Entry；扩为 64 项时改成了 4 B Entry。**这是 11 月 25 日 22:23 SII 更新中引入的格式回归，不只是尚未重生成名称。**

### 6.3 为什么它能与 CoE 通过并存

上游 [映射选择](https://github.com/OpenEtherCATsociety/SOEM/blob/49fc34923b973c17700592319159af22157350c9/src/ec_config.c#L572) 只有在 CoE/SoE 等没有得到位数时才回退 SII。CoE 在线 2048/2048 bit 成功时，SII PDO 类别的错误可能暂时不参与建图。

一旦邮箱数据读取失败、PREOP 未完成或 CoE 超时，回退 SII 又得到错长，主站就可能按错误长度配置 SM；从站 [CheckSmSettings](E:/Zephyr/zephyr_user/midlayer/ethercat/core/ecat_device.cpp#L1049) 仍要求 256 B，于是出现 `0x001E`（输入 SM 配置）或 `0x001D`（输出 SM 配置）。

**它是故障放大器：先有 CoE 路径失败，错误 SII 又把失败转成 SM 长度错误。强制重写 SM 长度不能自动纠正已经按错误位数配置的 FMMU 和 IOmap。**

另外，数组 2080 B 与常量 `kSiiSizeBytes=0x800` 的 2048 B 不一致也应记录，但超出的末尾为 `0xFF`，当前只读实现使用 `sizeof(aEepromData)` 处理边界；没有证据表明这 32 B 尾部差异单独造成当前 CoE 失败。

## 7. 从站协议栈六处差异究竟改变了什么

失败栈 `8dab046` 相对当前通过栈的差异如下：

| 文件/修改 | 机制与判断 |
|---|---|
| `ecat_device.cpp`：去掉邮箱 SM 使能检查；过程 SM 不再按 enabled 分支验证 | 通过放宽校验推进状态，不能修复主站未正确配置或状态未到达；两版仍要求非零 256 B 长度，故错误 SII 长度不会因此变正确 |
| `ecat_device.cpp`：SII 自检、失败 SM 回读日志 | 主要提供观察；有额外读取和日志开销，但没有证据表明它单独导致历史故障 |
| `al/ecat_sm.cpp/.hpp`：新增 `WriteSyncManager` | 快照中只见声明/定义，没有调用点，不能把未调用函数当作实际改坏 SM 的来源 |
| `EnableSyncManagerChannel`：多写 `SM +6` 的 activate 字节 | 主站配置权限不能靠从站 PDI 补偿；且当前 HAL 对非对齐写会扩成对齐 dword 读改写，实际触及范围比表面 1 B 大，需硬件权限证据后才能定责 |
| `mailbox/ecat_mailbox.cpp`：增加 receive_locked 补取 | 是接收延迟场景的补偿；当前通过栈没有这项仍可通过，反证它不是所有配置下必需的“CoE 开关” |
| `mailbox/ecat_sii_service.cpp`：不管 advertised width，固定回 8 B | 若 ESC 声明 4 B 并且主站按 4 B 读取，写多 4 B 不能自动修正状态时序；未提供 advertised width/请求响应同轮数据，不能认定为唯一修复 |
| `model/ecat_dictionary.cpp`：INIT/BOOT 允许按 PREOP 权限读 SDO | 只改变字典访问判断，不会启动未运行的 mailbox。它在掩盖主站提前读的问题，不能替代 PREOP 真正完成 |

失败栈在“放宽检查”“补取接收”“强制宽度”“增加诊断”之间同时改动，导致单次通过或失败不能定位到其中某一项。

### 7.1 当前通过栈仍有共有风险，但不能全部定为这次根因

- [Poll 与 OnPdi](E:/Zephyr/zephyr_user/midlayer/ethercat/core/ecat_device.cpp#L162) 都直接调用 `HandleAlEvents`。进入 SAFEOP 的过程中被 ISR 插入 OP 处理，存在重入/状态竞争路径。它两版共有，需要运行现场才能区分与主站未等待的贡献。
- [BackToInit 分支](E:/Zephyr/zephyr_user/midlayer/ethercat/core/ecat_device.cpp#L529) 只做 `BackToInit/SetState`，没有像逐级退出路径那样调用 `LeavePreOp` 并发布新状态；[Mailbox::Stop](E:/Zephyr/zephyr_user/midlayer/ethercat/core/mailbox/ecat_mailbox.cpp#L173) 才会释放队列、复位计数。因此热重连/从 OP 回 INIT 仍有状态残留风险。两份快照都保留该路径，冷启动能通不等于热重连已通。
- [WritePdiControl](E:/Zephyr/zephyr_user/midlayer/ethercat/core/al/ecat_sm.cpp#L64) 注释说“只改 PDI 字节”，实际先读四字节再写四字节；底层寄存器各字节的可写权限和副作用必须按芯片手册核对，不能仅凭注释断言全写无害或必然损坏。
- [HPM HAL Write](E:/Zephyr/zephyr_user/zephyr/drivers/ethercat/hal/hpm/ecat_hal_hpm.cpp#L445) 非对齐写会读改写整字，这是确实存在的访问行为，但与当前通过版相同。

这些风险值得后续分项验证，却不能作为“当前一定收发不了”的依据。当前已通过的实测本身就是反例，必须保留其适用条件。

## 8. 为什么后面会退化到 PREOP/CoE 都过不了

### 8.1 有历史记录支持的直接回归：ISR-only

既有 [《EtherCAT 本轮问题复盘与逐行修改方案》](EtherCAT本轮问题复盘与逐行修改方案-2026-11-26.md) 记载：一轮调试把事件处理改为只依赖 ISR 锁存，同时关闭 Poll 的硬件事件读取；实际连续日志为 `PDI_ISR_total=0`，主站已分配站地址，但从站仍 INIT，SDO `0x1C00:0` 和 `readPDOmap` 失败。

这个机制本次有额外源码支持：

1. 当前及失败快照初始化都执行 `ResetALEventMask(0)`，把 PDI 事件掩码清零。
2. `StartEvents()` 只开 CPU IRQ 和定时器，不重设 AL Event Mask。[初始化](E:/Zephyr/zephyr_user/midlayer/ethercat/core/ecat_device.cpp#L130)、[StartEvents](E:/Zephyr/zephyr_user/zephyr/drivers/ethercat/hal/hpm/ecat_hal_hpm.cpp#L364)
3. 恢复 AL Control/EEPROM/过程数据事件 mask 的调用在 `EnterSafeOp` 后段，且代码没有显式启用 mailbox 事件 mask。[SAFEOP 设置](E:/Zephyr/zephyr_user/midlayer/ethercat/core/ecat_device.cpp#L831)
4. 所以在主站没有额外替从站配置 PDI mask 的条件下，INIT/PREOP 阶段很依赖 Poll 推进。仅删 Poll、保留原初始化，并不能获得可运行的 ISR 模式。

**若历史日志与对应改动准确，这次最后停 INIT 的直接原因是事件处理链被切断；CoE 失败是它的下游结果。** 该修改不在本次 Stack-fail `8dab046` 快照里，不能说“8dab046 本来就是 ISR-only”。

### 8.2 把 AL Event 当成 read-to-clear，导致修复方向跑偏

已有早期文档和契约注释把“读 AL Event Request”写成“读即确认”。同一复盘后来已经更正：读取 `0x0220` 本身不清事件，AL Control Event 由读 `0x0120` 等对应动作确认，邮箱/过程数据由相应 SM 缓冲访问确认。

因此“诊断额外读了 AL Event，所以抢走了事件”不能直接成立；真正应排查的是**谁执行了确认动作、谁修改了状态机、是否重入、是否没有任何路径在处理**。[Beckhoff 官方 ESC 寄存器说明](https://download.beckhoff.com/download/Document/io/ethercat-development-products/ethercat_esc_datasheet_sec2_registers_3i0.pdf)

把只读观察误当事件消费，再用 ISR-only 替换 Poll，会把原来的“偶发时序/调度问题”升级为“根本不处理 PREOP 请求”。

### 8.3 用错误现象追错层次

几种相似数字必须分开：

| 位置 | 值 | 含义 |
|---|---|---|
| AL Status `0x0130` | `0x0011` | INIT (`0x01`) 加错误位 (`0x10`) |
| AL Status Code `0x0134` | `0x0011` | Invalid AL Control，即非法状态跳转 |
| AL Control `0x0120` | `0x0011` | 请求 INIT + error ACK |
| AL Control `0x0120` | `0x0012` | 请求 PREOP + error ACK |

同为 `0x0011` 不能跨寄存器互相解释。站地址 `0x1001` 证明 ESC 收到了配置写，也不能证明从站 C++ 状态机或邮箱已经处理。

## 10. 最可信的故障演进链

下面区分已确认路径与推断连接，不把缺失的时间顺序补造成事实：

```text
已确认：应用切换到 v2，启用 chassis / CAN TX
  └─ CAN 队列有消息但不消费，K_NO_WAIT 线程空转
      ├─ 确定：电机 CAN 发送函数不运行
      └─ 推断：ECAT Poll/SII/CoE 服务延迟增大

已确认：主站两个快照都不显式等待 PREOP 后再做独立 CoE 诊断
  └─ 可能出现诊断 ret=0，正式 config_map 随后却成功

已确认：主站直接请求 OP，未确认 SAFEOP
  └─ 与从站转换/调度窗口叠加时，可触发非法跳转 0x0011

已确认：22:23 SII 更新把 PDO Entry 写成 4 B
  └─ 一旦 CoE 没得到映射，SII 回退生成错误大小
      └─ SM 长度校验报 0x001D/0x001E，进一步被误判为业务 PDO 长度错误

历史记录：继续修改事件处理，撤掉 Poll 并改 ISR-only
  └─ 实际 ISR 未运行/事件 mask 未配齐
      └─ INIT/PREOP 不推进
          └─ 此时所有 SDO/PDO 映射自然失败

恢复阶段：撤除业务/CAN干扰，回到图案收发基线
  └─ 再通过调整主站 SDO 探测时序确认 CoE 2048/2048 bit
      └─ 说明映射定义能工作，不代表所有业务及重连路径都已验收
```

这比“PDO 字节布局改坏了”更能同时解释：同样 256 B、同样 HAL，有时 CoE 能通、有时 PREOP 不走、有时 OP 只在重试后成功，以及电机功能仍不工作。
